## Major

### Evidence can establish a fact for the wrong intake, `src/data/programs/schema.ts:667`

**Problem**: Program evidence is checked against the institution hostname, but its `applicability.intakeId` is never compared with the containing program. Changing the first program title's evidence intake from `september_2027` to `september_2028` still passes `assertCatalogRelease`.

**Why it matters**: A fact from another intake becomes trusted release data. This violates the applicability boundary in AC-3 and AC-5 and key invariant 5.

**Suggested fix**: You could validate each cycle specific evidence record against the containing program's intake, retain exact fact paths in errors, and cover a mismatched intake in the regression checks.

### Subject and test registries are not enforced, `src/data/programs/schema.ts:161`

**Problem**: IB subjects and admissions tests accept any snake case identifier. Admissions results at line 191 accept any number without a test specific scale or unit. A mutation using `made_up_subject`, and another using `made_up_test` with result `-999`, both pass the full release gate. Supported condition values likewise accept arbitrary strings without checking the vocabulary of the selected field.

**Why it matters**: Later rule evaluation cannot rely on the normalized IDs or score bounds promised by the spec. Unsupported rules may be admitted with `evaluation: automatic`, bypassing the manual review safeguard.

**Suggested fix**: You could introduce the approved versioned subject and test registries, validate result units and bounds through the selected test, and validate condition values and operators against their field. Unknown vocabulary should fail validation or follow the explicit unsupported condition path.

### Release validation permits unestablished selection facts, `src/data/programs/schema.ts:393`

**Problem**: The fact wrapper allows `degreeLevel` and `instructionLanguage` to be unknown, and the release gate does not require these identities to be known. Replacing both facts on the first program with properly evidenced unknown facts still passes `assertCatalogRelease`.

**Why it matters**: The release command can certify 24 English taught undergraduate programs without establishing that every selected program is undergraduate or English taught. This breaks AC-1 even though structural unknowns may be useful during curation.

**Suggested fix**: You could keep unknowns available for structural records but require the identity facts that determine release eligibility to be known at the release boundary.

### The promised single record validation boundary is missing, `src/data/programs/schema.ts:472`

**Problem**: The exported API provides `parseProgramCatalog`, but no `parseProgramRecord`. Local duplicate requirement and field checks exist only inside full release validation. A catalog containing duplicate local requirement IDs passes `parseProgramCatalog`; importing `parseProgramRecord` returns no export.

**Why it matters**: The specified curator and small fixture workflow cannot validate one program independently. Consumers using structural parsing receive records that violate the explicitly promised local ID contract.

**Suggested fix**: You could expose the specified single record parser and move program local integrity checks into a reusable structural validator. The release validator can then add global selection and coverage checks. Cover duplicate local IDs and a valid one program fixture separately from release counts.

### Valid group references depend on requirement type order, `src/data/programs/schema.ts:682`

**Problem**: The validator collects IDs for one coverage type, then validates that type's groups immediately. A group in `academic_threshold` referring to the same program's `math_aa_hl_7` fails as an unknown reference because `subject_prerequisite` has not been visited yet. The same reference is valid under the spec, which permits references to requirements anywhere in the same program.

**Why it matters**: Legitimate combined academic rules cannot be represented consistently. Rejection depends on the order of `REQUIREMENT_TYPES`, rather than whether the referenced requirement exists.

**Suggested fix**: You could collect and validate all local requirement IDs before checking any groups. Cover both forward references and genuinely absent references.

## Minor

### Deadline time and timezone values are not validated, `src/data/programs/schema.ts:208`

**Problem**: `localTime` checks only the text shape, and `timeZone` accepts any nonempty string. Setting an existing deadline to `99:99` and `made_up_zone` passes the release gate.

**Why it matters**: A curator typo can reach later date calculations as a supposedly validated deadline and produce invalid dates or timezone exceptions.

**Suggested fix**: You could validate clock ranges and supported IANA names, with regression examples for invalid values.

### Program ordering does not enforce the specified subject mapping, `src/data/programs/schema.ts:399`

**Problem**: Subject definitions are checked against their prescribed numeric keys, but each program's copied `subjectSortKey` is not checked against its subject. Changing the first computer science program's key to `9999` passes release validation and moves it out of its subject block. String tie breaks also use locale collation at line 728 rather than the specified ordinal comparison.

**Why it matters**: The release gate permits inconsistent subject ordering even though the subject registry is valid, and the tie break does not implement the agreed ordering contract.

**Suggested fix**: You could validate or derive each program's subject key from the subject registry and share an ordinal ID comparator across the loader and its tests.
